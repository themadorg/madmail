Madmail теперь автоматически публикует тестовые сборки отдельно от стабильных версий с цифровой подписью. Если ваш сервер обслуживает пользователей, продолжайте использовать стабильный канал. Если хотите помочь с проверкой изменений, выберите релиз с пометкой `unstable` и запустите его в тестовой среде.

[Автоматизацию релизов из PR #210](https://github.com/themadorg/madmail/pull/210) дополнила [расширенная матрица сборки из PR #218](https://github.com/themadorg/madmail/pull/218). Теперь тестовые релизы включают несколько вариантов сборок для Linux amd64 и ARM64, а также пакеты для Windows. Те же процедуры сборки запускаются и для пул-реквестов (PR), поэтому ошибки сборки и упаковки можно заметить ещё при проверке изменений.

## Откуда берётся номер версии

Не каждое слияние требует нового релиза. Автоматизация использует Conventional Commits, чтобы определить, нужно ли повышать версию и какую часть номера менять:

| Изменение | Повышение версии |
| --- | --- |
| `fix`, `perf`, `revert` | Patch, третья часть номера |
| `feat` | Minor, вторая часть номера |
| Изменения, нарушающие совместимость | Major, первая часть номера |
| `docs`, `chore`, `ci`, `test` | Обычно без изменения версии |

В манифестах исходного кода остаётся числовая версия `X.Y.Z`. Тестовые теги Git и предварительные релизы GitHub получают суффикс: `vX.Y.Z-unstable`. Стабильные релизы используют `vX.Y.Z`.

Подготовка релиза зависит от успешного прохождения проверок CI, а публикация требует успешной сборки. После этих проверок сборку можно передавать на тестирование. Сам по себе успешный CI не гарантирует отсутствия ошибок или пригодности для рабочего сервера.

## Полная матрица сборки в каждом PR

Для каждого PR теперь запускается полная матрица из шести вариантов тестовой сборки в режиме `build-only`. Каждая задача берёт один и тот же явно указанный коммит PR и использует его `Cargo.lock` и зафиксированную ревизию веб-интерфейса администрирования. Задача для Windows собирает сервер, приложение для трея и тестовый установщик вместе.

Итоговая проверка требует успешного завершения всех задач матрицы. Затем она подготавливает комплект из 16 файлов и сохраняет его как артефакт GitHub Actions с именем `unstable-build-only-validated`. Задачи для PR имеют доступ к репозиторию только на чтение и не получают учётных данных для публикации. Они не повышают версию, не создают теги или релизы и не публикуют Docker-образы. Общедоступные тестовые релизы по-прежнему выходят после слияния в `main` изменений, требующих выпуска, и успешного прохождения проверок публикации.

При проверке PR доступны результаты сборки и упаковки всех вариантов. При этом проверки запуска охватывают не все варианты: серверы для ARM64 собираются кросс-компиляцией, но в этой матрице не запускаются. Для установщика Windows имитируют наличие установленной копии и проверяют, что он отказывается продолжать. Полную установку этот тест не выполняет. Проверка на целевой системе по-прежнему нужна.

## Что входит в тестовый релиз

На GitHub тестовые сборки явно отмечены как предварительные релизы. Их исполняемые файлы не подписаны и могут содержать регрессии или несовместимые изменения. Совместимость при обновлении и откате не гарантируется, поэтому для проверки выбирайте среду, которую можно создать заново, а не сервер, от которого зависят пользователи.

Два файла помогают определить происхождение сборки и проверить скачанное. `SOURCE.txt` указывает ревизию исходного кода, использованную при сборке. В `SHA256SUMS` записаны контрольные суммы, с которыми можно сравнить скачанные файлы.

Совпадение контрольной суммы означает, что файл соответствует значению, опубликованному вместе с релизом. Это помогает проверить целостность файла, но не заменяет цифровую подпись, которую требует встроенный механизм обновления стабильных версий.

Расширенный комплект уже доступен в таких релизах, как [v2.38.0-unstable](https://github.com/themadorg/madmail/releases/tag/v2.38.0-unstable). Он включает шесть сборок сервера:

| Сборка сервера | Исполняемый файл |
| --- | --- |
| Linux amd64, glibc | `madmail-linux-amd64` |
| Linux amd64, legacy, полностью статическая сборка с glibc | `madmail-linux-amd64-legacy` |
| Linux amd64, musl | `madmail-linux-amd64-musl` |
| Linux ARM64, glibc | `madmail-linux-arm64` |
| Linux ARM64, musl | `madmail-linux-arm64-musl` |
| Windows amd64 | `madmail-windows-amd64.exe` |

Для каждой сборки Linux также есть архив `.tar.gz` с исполняемым файлом под именем `madmail`. Сервер для Windows доступен и в архиве `madmail-windows-amd64.zip`. Приложение для трея и неподписанный тестовый установщик Windows публикуются как `madmail-tray-windows-amd64.exe` и `madmail-windows-amd64-setup.exe`.

Выбирайте файл для своей операционной системы и архитектуры процессора, а в Linux также учитывайте вариант libc.

Итого загружается 16 файлов: шесть исполняемых файлов сервера, шесть архивов, приложение для трея, установщик, `SOURCE.txt` и `SHA256SUMS`. GitHub добавляет [два автоматически создаваемых архива исходного кода](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases), поэтому на странице релиза получается 18 позиций для скачивания. При выборе платформы или пакета смотрите фактический список файлов конкретного релиза: у старых выпусков комплект может отличаться.

Неподписанный установщик обозначен как `Madmail TESTING` и предназначен для чистой временной виртуальной машины Windows. Он отказывается продолжать, если обнаруживает существующую установку Madmail, его службу или данные. Запускайте его в отдельной тестовой среде.

## Проверка подписи в стабильном канале сохраняется

Для стабильных серверных сборок есть отдельный процесс сборки и цифровой подписи. Он использует выбранную ревизию исходников и инструменты, которые владелец проекта поддерживает отдельно. Ключи подписи стабильных релизов хранятся вне публичного репозитория и публичного CI.

Штатный механизм обновления продолжает работать со стабильными подписанными версиями. Команды `madmail update` и `madmail upgrade` пропускают черновики и предварительные релизы GitHub, а проверка подписи Ed25519 по-прежнему обязательна. Публикация неподписанной тестовой сборки не делает её доступной для установки через эти команды.

Установочный пакет стабильной версии для Windows использует подписанный исполняемый файл сервера и соответствующее приложение для трея, прикреплённые к тому же стабильному релизу.

## Для Docker действуют те же каналы

У каждого канала Docker есть теги конкретных версий и плавающий тег:

| Канал | Тег конкретной версии | Плавающий тег |
| --- | --- | --- |
| Тестовый | `X.Y.Z-unstable` | `unstable` |
| Стабильный | `X.Y.Z` | `latest` |

Плавающий тег следует за выпусками своего канала, а тег версии позволяет выбрать конкретный релиз. Для рабочих серверов используйте стабильные теги. Выбирая `unstable`, вы намеренно переходите на тестовый канал.

Тестовый образ публикуется только после успешной публикации соответствующего предварительного релиза GitHub. Процесс публикации тестовых сборок не меняет `latest`. Проверки в CI также должны предотвращать откат плавающего тега при повторном запуске старой задачи.

Для файлов релиза тоже есть правила повторной публикации. Уже прикреплённый файл можно использовать повторно, если он совпадает с ожидаемым. Если содержимое отличается, задача завершается с ошибкой, а не незаметно заменяет файл.

Для Docker-образов с тегом версии проверяется соответствие исходной ревизии. Ошибка реестра образов или аутентификации останавливает операцию и не считается разрешением перезаписать образ.

## Что указать в отчёте об ошибке

Опубликованная тестовая сборка позволяет другим участникам скачать тот же вариант и попробовать воспроизвести проблему. Если вы нашли ошибку, укажите:

- Тег релиза или номер PR, если вы использовали артефакт его рабочего процесса, и ревизию исходного кода из `SOURCE.txt`.
- Операционную систему, архитектуру и точное имя исполняемого файла, а при использовании Docker также тег образа.
- Шаги для воспроизведения проблемы, ожидаемый и фактический результат.
- Нужные фрагменты логов, предварительно удалив учётные данные и личную информацию.

Сборки доступны в [списке релизов](https://github.com/themadorg/madmail/releases), а сообщить о проблеме можно через [GitHub Issues](https://github.com/themadorg/madmail/issues). Перед скачиванием посмотрите пометки релиза, его описание и доступные файлы.
